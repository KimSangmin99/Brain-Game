# Vercel + Supabase 연결·배포 안내

2026-11-09. 사용자가 Vercel 프로젝트 `brain-game`, Supabase 프로젝트 `jetqqkjamutdctehvzfx`의 초기 SQL과 DATABASE_URL 설정·배포를 완료했다고 확인했다. 이번 작업 환경에는 운영 DB 자격 증명이 없으므로 새 계정 기능의 실제 운영 연결 검증은 아직 수행하지 않았다. 게스트 플레이는 외부 DB 없이 동작하고 기록은 브라우저에 저장된다.

## 1. 연결 대상과 인증

대상 저장소는 `KimSangmin99/Brain-Game`이다. 먼저 기존 Supabase 프로젝트 URL/ref와 Vercel 프로젝트 이름·팀을 확인한다. 비밀번호·토큰·DB URI는 채팅·Git·빌드 로그에 남기지 않는다.

클라우드 작업 환경에서 관리 API로 연결 상태를 점검하려면 보안 설정에 `SUPABASE_ACCESS_TOKEN`과 `VERCEL_TOKEN`을 등록한다. 각각 `api.supabase.com`, `api.vercel.com`에 사용하도록 제한한다. 환경 설정 초안에 이름을 추가한 것과 실행 환경에 인증이 적용된 것은 다르다. 사용자가 환경 설정을 검토·게시한 뒤 새 실행 환경에서 인증 준비 상태를 확인한다. 이 환경 게시는 앱의 Vercel 배포와 별개다.

관리 API 토큰은 프로젝트 설정 작업용이다. 웹 앱 런타임에 넣지 않는다. HTTPS 프록시가 주입하는 토큰 자리표시자는 PostgreSQL 비밀번호로 사용할 수 없다. DB URI는 Vercel 환경변수 또는 마이그레이션 실행기의 안전한 비밀값 저장소에 실제 자격 증명으로 설정한다.

## 2. 서버 환경변수

| 이름 | 설정 위치 | 용도 |
| --- | --- | --- |
| DATABASE_URL | Vercel 서버 런타임 | Supabase Connect 화면의 트랜잭션 풀러 URI, 일반적으로 6543 포트 |
| DIRECT_DATABASE_URL | 신뢰할 수 있는 마이그레이션 실행 환경 | 직접 연결 또는 세션 풀러 URI, 일반적으로 5432 포트 |
| DATABASE_CA_CERT | 필요한 실행 환경 | 공급자가 제공한 신뢰할 PEM CA. 시스템 신뢰 저장소로 검증되면 생략 |
| APP_ORIGIN | 필요 시 Vercel 서버 런타임 | 변경 요청을 허용할 정확한 사이트 origin(경로 없이 HTTPS URL). 생략 시 요청 사이트 기준. Preview에는 운영 origin을 복사하지 않음 |
| CRON_SECRET | 추후 예약 작업 구현 시 | 예약 작업 인증. 현재 엔드포인트나 예약은 없음 |

Preview와 Production의 DB를 분리한다. Preview에 운영 DB 자격 증명을 복사하지 않는다. 프로젝트의 실제 Connect 화면 값을 사용하고 특수문자가 있는 비밀번호는 URI 형식에 맞게 인코딩한다. 직접 연결의 IPv6 지원이 실행 환경과 맞지 않으면 지원되는 세션 풀러를 선택한다.

DB 변수에 `NEXT_PUBLIC_` 접두사를 붙이지 않는다. `.env.example`에는 이름만 있으며 실제 `.env*`는 Git에서 제외된다. `DATABASE_URL`은 DB 모듈을 처음 사용할 때만 필요하므로 현재 게스트 화면과 빌드는 자격 증명 없이도 실행된다.

서버 연결은 prepared statement를 끄고 인스턴스당 연결을 1개로 제한한다. 전체 함수 인스턴스의 합산 연결 수와 프로젝트 제한은 실제 부하로 점검한다. 외부 DB TLS 인증서 검증을 끄지 않는다.

## 3. 원격 적용 전 확인

1. 프로젝트 ID·소유 팀·리전·PostgreSQL 버전·기존 앱 사용 여부를 읽기 전용으로 확인한다.
2. 백업·복구 수단과 `app_private` 스키마 및 Drizzle 이력 테이블의 기존 사용 여부를 확인한다. 이름 충돌이 있으면 초기 SQL을 그대로 적용하지 않고 기존 구조와 대조한다.
3. Preview용 별도 DB에서 아래 마이그레이션을 먼저 실행한다. 초기 파일은 새 스키마·테이블을 만들며 기존 테이블 삭제 명령을 포함하지 않는다.
4. 실제 풀러 연결, TLS 검증, 테이블·인덱스·제약과 Data API 접근 차단을 검증한다. `npm run test:db`의 PGlite 검증만으로 원격 검증 완료라고 표시하지 않는다.

```sh
npm ci
npm run test:db
npm run db:migrate
```

`db:migrate`는 `DIRECT_DATABASE_URL`을 요구하고 6543 포트를 거부한다. 적용 이력으로 같은 마이그레이션을 재실행하지 않는다. `db:generate`는 스키마 변경을 SQL 파일로 생성할 뿐 원격 DB에 적용하지 않는다. 이미 적용한 파일은 수정하지 않고 새 마이그레이션을 만든다. 운영 변경은 백업·검토 후 별도로 적용하며 `npm run build`에서 실행하지 않는다.

## 4. 데이터 접근과 인증

`app_private`를 Supabase Data API의 노출 스키마에 추가하지 않는다. 초기 테이블 9개는 RLS를 활성화하고 PUBLIC·anon·authenticated 접근을 회수한다. 이 앱은 브라우저에서 Supabase Data API를 직접 호출하지 않으며 anon 키나 service-role 키가 현재 필요하지 않다.

회원 인증은 자체 ID·비밀번호·서버 세션으로 구현했다. Supabase Auth용 가짜 이메일을 만들지 않는다. 서버가 사용자의 세션과 데이터 소유권을 검증해야 하며, DB 소유자 권한은 RLS를 우회할 수 있음을 전제로 접근을 제한한다. 로그인·기록 API는 세션과 계정 일치를 확인하고 개인 결과만 조회한다. 클라이언트 결과는 전부 imported/unverified로 저장해 공식 순위에서 제외한다.

## 5. Vercel 프로젝트 설정

- 기존 프로젝트와 Git 저장소 연결 상태, Root Directory, 배포 브랜치·자동 배포 설정을 먼저 확인한다.
- Node.js 24, Next.js 프레임워크, `npm ci`, `npm run build`를 사용한다. 저장소 루트의 `vercel.json`에 빌드 설정이 있다.
- DB를 사용하는 Route Handler는 Node.js 런타임에서 실행한다. 함수 리전은 Supabase DB와 가깝게 선택하고 실제 지원 설정을 확인한다.
- 현재 상주 워커나 Cron은 없다. 메일·만료 처리는 추후 인증된 짧은 예약 작업과 DB lease·중복 방지로 구현한다. 요금제별 실행 시간·예약 주기는 도입 시 확인한다.
- Preview 배포에서 모바일·PC 게임, 저장·재접속, 서버 로그의 비밀값 제외 여부를 확인한다. 공개 Production 배포는 별도의 배포 단계로 취급한다.

## 6. 완료 기록

연결 완료 보고에는 확인한 프로젝트 이름/ref, 적용한 마이그레이션 이름, 실제 DB 검증 결과, 배포한 경우 URL·대상 환경을 남긴다. 토큰·URI·비밀번호는 남기지 않는다. GitHub 커밋·푸시, 클라우드 환경 게시, Supabase 마이그레이션, Vercel 배포는 각각 수행 여부를 구분한다.


## 7. 이번 계정 기능 업데이트 적용

초기 SQL `0000_initial_private_schema.sql`을 이미 실행했다면 다시 실행하지 않는다. 이번 변경은 `drizzle/0001_accounts_and_limits.sql`이다. 요청 제한용 auth_limits 테이블과 users의 안내 확인 버전·시각 2개 열을 추가하며 기존 데이터는 삭제하지 않는다.

마이그레이션 명령으로 적용하는 권장 순서:

```sh
# DIRECT_DATABASE_URL을 안전한 실행 환경에 등록한 뒤, 초기 SQL만 수동 실행한 DB에서 1회
npm run db:baseline -- --through=0000
npm run db:migrate
```

baseline은 선택한 SQL을 로컬 PostgreSQL 호환 엔진에 적용한 뒤 대상 DB의 열·기본값·제약·인덱스·RLS·Data API 역할 권한을 대조한다. 일치할 때만 drizzle 이력 테이블을 등록한다. 앱 테이블이나 기존 기록은 변경하지 않는다. 구조 차이나 기존 이력이 있으면 중단한다. PostgreSQL 버전 차이로 카탈로그 표현이 다른 경우에도 임의로 통과시키지 않고 차이를 검토한다.

CLI용 연결을 설정하기 어렵다면 [SQL Editor용 파일](sql/account-update.sql)의 전체 내용을 Supabase SQL Editor에 붙여 한 번 실행한다. 이 파일은 0001 SQL을 BEGIN/COMMIT으로 감싼 것으로, 초기 SQL 0000이 이미 적용된 DB용이다. 0001이 적용됐다면 반복 실행하지 않는다. 실패하면 `ROLLBACK;` 후 원인을 확인하며 CREATE TABLE을 반복하지 않는다. 이 방식으로 0000과 0001을 수동 적용했다면 이후 CLI 사용 전에 아래 명령으로 두 파일의 구조와 이력을 맞춘다.

```sh
npm run db:baseline -- --through=0001
```

SQL 적용 후 새 코드를 Vercel에 배포한다. 기존 DATABASE_URL 외에 로그인용 토큰·Supabase Auth 키·SESSION_SECRET을 추가할 필요는 없다. 쿠키에는 256비트 무작위 세션 토큰, DB에는 SHA-256 해시만 저장한다. 운영 쿠키는 Secure·HttpOnly·SameSite=Lax·__Host- 접두사를 사용한다.

운영 확인 순서:

1. 회원가입 → 로그아웃 → 로그인 → 새로고침 후 계정 유지.
2. 계정 화면에서 게스트 기록 개수 확인 → 가져오기 선택 → 기록·단계 합집합 확인.
3. 별도 브라우저에서 로그인 → 완료 기록과 열린 단계 확인.
4. 로그인한 상태로 게임 완료 → 계정 저장 메시지 → 별도 기기에서 결과 확인.
5. 다른 계정에는 기록이 보이지 않는지 확인. 저장 실패 시 계정 화면의 다시 동기화를 사용한다.

현재 서버는 완료 기록만 동기화한다. 진행 중 문항은 계정별 로컬 저장소에 보관한다. 게스트 원본은 병합 영수증 확인 후 7일 동안 보관하고 다음 게스트 기록 조회 시 제거한다. 실패한 기록은 삭제하지 않는다. 이 브라우저에서 다른 계정에 연결됐다고 표시된 기록은 가져오기 목록에서 제외하며, 서버도 전역 attempt ID와 병합 영수증으로 교차 계정 연결을 거부한다.

가입·로그인은 DB 기반 제한을 먼저 예약해 동시 요청도 제한한다. ID별 5회/15분, IP별 30회/15분의 보수적 시도 제한이며 로그인 성공 시 ID 제한은 초기화한다. 가입은 IP별 10회/시간이다. 만료된 제한 키는 후속 요청에서 제한된 묶음으로 삭제한다. 비밀번호 차단 목록은 현재 소규모 로컬 목록이며 출시 전 보강이 필요하다.

정식 공개 출시 전에는 운영자·문의처·보관·삭제 절차가 명시된 이용약관·개인정보 처리방침, 복구·탈퇴 흐름을 완성해야 한다. 현재 계정 안내는 개발 버전의 기능·수집 범위와 제한을 설명한다.


## 8. 규칙 분석 추가

사용자가 계정 업데이트 SQL 적용 완료를 확인했다. 규칙 분석은 기존 attempts.game_id 제약에 포함돼 있고 JSON payload를 사용하므로 이번 게임 추가에 별도 SQL은 없다. 코드 배포 후 규칙 분석 완료 → 기록 목록 → 다른 기기 로그인 → 규칙 분석 2단계 개방을 확인한다. 기존 운영 원격 DB는 이 작업에서 직접 접속하지 않았다.


## 9. 코드 브레이커 추가

기존 game_id 제약과 JSON payload를 사용하므로 추가 SQL·환경변수는 없다. code-v1은 한 코드 결과(answers 1개)로 서버 검증과 점수 계산을 수행한다. 배포 후 예제 → 추측 → 해독 → 다음 단계 → 계정 기록 → 다른 기기 조회를 확인한다. 새로고침에서는 같은 코드·이전 추측·작성 중 답을 유지해야 한다. 운영 배포 성공 여부는 Vercel 대시보드에서 별도로 확인한다.


## 10. 조건 배열 추가

arrangement-v1 / arrangement-content-v1은 기존 game_id와 JSON payload를 사용하므로 추가 SQL·환경변수는 없다. 배포 후 예제 → 배치·교환 → 틀린 제출·조건 설명 → 수정 후 해결 → 다음 단계 → 계정 기록 → 다른 기기 조회를 확인한다. 수정 후 해결은 10000점이고 도움 사용으로 구분돼야 한다. 새로고침은 같은 문제·배치·피드백을 보존한다. 운영 배포 성공은 Vercel 대시보드에서 별도로 확인한다.


## 11. 경로 설계 추가

route-v1 / route-content-v1과 검수 지도 은행을 추가했다. 기존 game_id와 JSON payload를 사용하므로 추가 SQL·환경변수는 없다. 배포 후 예제 → 경로 입력·되돌리기 → 필수 지점·순서·상한 피드백 → 수정 → 결과의 제출/예시 전환 → 계정 저장·다른 기기 조회를 확인한다. 더 긴 유효 경로도 통과하고 점수는 8000+floor(2000×L/S)로 저장돼야 한다. 새로고침은 같은 지도·초안·피드백을 보존한다. 운영 배포 성공은 Vercel 대시보드에서 별도로 확인한다.


## 12. 신호 탐색 추가

search-v1 / search-content-v1의 생성·3보드 점수·복구를 추가했다. 기존 game_id와 JSON payload를 사용하므로 추가 SQL·환경변수는 없다. 배포 후 예제 → 선택/취소 → 확정 전 정오 비노출 → 보드별 TP/FP/FN → 평균 결과·회고 → 계정 저장·다른 기기 조회를 확인한다. 신호 탐색의 answers는 3개이고 10000·10000·5000의 평균은 8333점으로 저장돼야 한다. 탐색 중 재접속은 미확정 보드만 바꾸고 완료한 보드와 점수를 보존한다. 운영 배포 성공은 Vercel 대시보드에서 별도로 확인한다.

## 13. 룰 스위치 추가

switch-v1 / switch-content-v1은 기존 game_id와 JSON payload를 사용하므로 추가 SQL·환경변수는 없다. 배포 후 예제 → 지시 안내 → 준비 → 자극·즉시 응답 → 시간 초과와 선택 오답 → 20문항 결과·회고 → 계정 저장·다른 기기 조회를 확인한다. 16개 정답·4개 시간 초과는 answers 20개·8000점으로 저장돼야 한다. 시간 제한 없는 자유 연습은 timing=untimed로 보존하며 단계 개방에 반영하지 않는다. 준비·안내 시간은 응답 시간에서 제외하고 자극 노출 중 재접속은 미확정 문항만 바꾼다. 운영 배포 성공은 Vercel 대시보드에서 별도로 확인한다.

## 14. 계정 관리·탈퇴 추가 (2026-11-13)

비밀번호 변경·모든 기기 로그아웃은 기존 0000·0001 구성으로 작동한다. 탈퇴에는 새 비공개 테이블을 만드는 `drizzle/0002_account_deletions.sql`이 필요하다. 이 파일은 기존 회원·게임 자료를 변경하거나 삭제하지 않는다. 새 환경변수·메일 서비스는 이번 기능에 필요하지 않다. SQL이 없으면 가입·로그인은 유지하고 탈퇴만 제공하지 않는다.

- SQL Editor에서 0000·0001을 직접 적용한 프로젝트: [계정 관리 업데이트 SQL](sql/account-management-update.sql)을 **한 번** 실행한다. 전체 초기 SQL이나 이전 업데이트를 다시 실행하지 않는다.
- 마이그레이션 이력을 사용하는 프로젝트: 대상 DB·백업·권한을 확인하고 안전한 `DIRECT_DATABASE_URL` 환경에서 `npm run db:migrate`를 실행한다.
- 수동으로 0002까지 적용했고 마이그레이션 이력이 없다면 `npm run db:baseline -- --through=0002`가 실제 구조·RLS·권한을 대조해 이력만 등록한다. 이력이 있다면 baseline을 재실행하지 않는다.

적용 후 페이지를 새로고침하고 내 계정 → 계정 보안·비밀번호·탈퇴 관리에서 탈퇴 버튼이 활성화되는지 확인한다. 별도 테스트 계정으로만 비밀번호 변경·기존 비밀번호 거부·다른 기기 세션 종료·기록 보존을 확인하고, 탈퇴는 삭제 범위·기기 원본 정리·ID 재가입 거부를 확인한다. 실제 회원 계정으로 시험하지 않는다. 운영 DB에 대한 마이그레이션·탈퇴·메일 발송은 이 작업 공간에서 실행하지 않았다.

삭제는 운영 DB에서 즉시 처리한다. 백업 순환만으로 삭제 계정이 되살아나지 않는다고 간주해서는 안 된다. 최신 삭제 원장을 복원 대상과 별도로 보존·재적용한 뒤 서비스 접근을 열어야 한다. [계정 관리 문서](accounts/security.md)의 전제와 복원 절차를 검토하고 운영 환경에서 검증한다.

`PLAYWRIGHT_BASE_URL=http://127.0.0.1:3100 npm run test:e2e -- --workers=2 e2e/account-management.spec.ts`로 실행 중인 로컬 프로덕션 빌드에서도 계정 관리 검사를 실행할 수 있다. 계정 API는 로컬 PGlite로 연결하며 운영 Supabase 검증을 뜻하지 않는다. 완료된 코드 푸시와 운영 Vercel 배포 성공은 별도이며 후자는 대시보드에서 확인한다.
